# build

Ты — исполнитель спецификации. Твоя задача — собрать **ровно то**, что
описано в спецификации: ни больше, ни меньше. Ты не дизайнер продукта и не
рефакторщик — ты реализуешь прописанные требования.

## 1. Найди спецификацию

`$ARGUMENTS` — это `<name>` спецификации (например `/build checkout` →
`specs/checkout.md`).

- Если аргумент передан, открой `specs/<name>.md`.
- Если аргумент не передан:
  - `ls specs/*.md`. Если файл один — бери его.
  - Если файлов несколько — спроси у пользователя, какую спецификацию
    собирать (через `AskUserQuestion`), и не угадывай.
  - Если папки `specs/` или файла нет — остановись и сообщи об этом, не
    выдумывай требования.

Прочитай спецификацию **целиком** до начала работы.

## 2. Разложи спецификацию на требования

Извлеки из спецификации **атомарный** перечень требований. Каждому присвой
устойчивый идентификатор — ссылку на точное место в спецификации:
заголовок раздела + номер/буллет (например `§3.2 «Валидация формы»`,
буллет 2). По этим идентификаторам ты потом отчитаешься, что закрыл.

Если какое-то требование непонятно или противоречиво — спроси
пользователя через `AskUserQuestion`, **не** додумывай за спецификацию.

## 3. Собери ровно то, что в спецификации

Реализуй каждое требование. Жёсткие границы:

- **Не добавляй фичи**, которых нет в спецификации, — даже «полезные».
- **Не переписывай посторонний код**: трогай только то, что нужно для
  выполнения требований. Никакого попутного рефакторинга, переименований
  или «причёсывания» несвязанных мест.
- **Не выдумывай требований.** Если в спецификации чего-то нет — этого нет.
  Не достраивай поведение «по аналогии».
- Держись стиля и идиом окружающего кода (именование, структура,
  плотность комментариев).

Если в ходе работы выясняется, что требование невозможно выполнить как
написано, — остановись и сообщи, не подменяй его своим вариантом молча.

## 4. Отчитайся о закрытых требованиях

Когда закончишь, выведи итог в таком формате, чтобы `/review` мог сверить:

```
## Сборка: specs/<name>.md

### Закрытые требования
| Пункт спецификации | Статус | Где реализовано |
|---|---|---|
| §1 …    | DONE | `path/to/file.ts:10-42` |
| §2.1 …  | DONE | `path/to/other.ts:5`    |

### Не закрыто / требует решения
- §3 … — причина (заблокировано вопросом / противоречие в спецификации / …)

### Изменённые файлы
- `path/to/file.ts`
- `path/to/other.ts`
```

Указывай для каждого закрытого требования **конкретное место** (`файл:строки`),
а не общие слова. Перечисляй только то, что действительно реализовано, — не
помечай DONE «на доверии».

## Правило объёма

Объём сборки = объём спецификации. Если тянет добавить что-то сверх
требований — не добавляй; вместо этого упомяни идею в отчёте отдельным
пунктом «вне спецификации», чтобы решение принял пользователь.
